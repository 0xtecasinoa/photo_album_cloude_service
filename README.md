# らくらく写真台帳

工事写真の撮影から台帳作成・共有・電子納品までを、ひとつのクラウドで完結させる建設業向けサービスです。

現場で撮影した写真は、撮影日時・電子小黒板の情報とともにそのままクラウドへ。
AI が黒板や手書き看板の文字を読み取り、工事写真台帳の作成から Excel / PDF 出力、
国土交通省の電子納品要領に沿った成果品の書き出しまでを自動化します。

## 主な機能

### 写真管理

- 撮影日時（EXIF `DateTimeOriginal`）を必ず保持し、台帳・一覧・並び替えの基準にします
- GPS 座標、カメラ機種、向き（Orientation）などの EXIF 情報を保存します
- SHA-256 による重複検出と、改ざん検知のための基準ハッシュを記録します
- 削除は論理削除。監査ログは削除後も残り、復元も可能です

### 電子小黒板（看板）

- 黒板テンプレートをブラウザ上で自由に設計できます
- 項目ごとに **文字サイズ・書体・太さ・文字色・背景色・字下げ・行間・縦横位置** を個別に設定できます
- ラベルと値のスタイルを別々に指定できます（実際の工事黒板の書式に合わせるため）
- 項目のデータ種別（項目カテゴリ）を選択できます
  - 手入力／選択肢から入力
  - 工事名・工事番号・発注者名・請負者名・施工場所（案件から自動入力）
  - 撮影年月日・撮影日時・撮影者・連番（撮影時に自動入力）
  - 工種・種別・細別・写真区分・撮影箇所・施工管理値
- 「（自動）」の項目は撮影時に自動で入り、現場では上書きできません
- 透過黒板（不透明度の調整）に対応しています
- テンプレートは管理者がロックでき、現場での書式崩れを防ぎます

### 手書き看板の取り込み

手書き看板を撮影した写真から項目を読み取り、黒板テンプレートの下書きを生成します。

`/templates/import` で看板の写真をアップロードすると、
項目名（工事名・工種・測点・施工者・日付など。表記ゆれも吸収します）と
記入内容を読み取り、確認画面に並べます。元の写真を左に置いているので、
見比べながら直せます。確信度の低い項目は赤く表示されます。

手書き文字の判別精度は文字の大きさ・書き方・撮影環境により変動するため、
**「読み取りの下書き → 人が確認・修正 → 確定」** というレビュー方式を採っています。
自動確定はしません。納品写真に誤った黒板が載ると、その現場の写真すべてが撮り直しになるためです。

#### 認識率

見本 10 枚（正対・明朝体・緑板・傾き・低解像度・低コントラスト・罫線なし・
黒板と傾きと低解像度の重ね合わせ・強圧縮・別内容）で測っています。

```bash
npm run bench:ocr
```

| | 項目の完全一致 | 文字の正解率 |
| --- | --- | --- |
| 対策前 | 62.9% | 70.4% |
| 現在 | **100%** | **100%** |

改善の内訳:

- **白文字の黒板を反転**してから読む。Tesseract は「明るい地に暗い文字」を
  前提にしており、緑板に白チョークという現場で一番多い形は 0/5 でした。
- **傾きを戻す**。数度の傾きでも行がまとまらず認識が崩れます。
  行ごとの暗い画素数のばらつきが最大になる角度を探しています。
- **英数字のモデルを併用**（`jpn+eng`）。日本語だけだと測点や日付の数字が
  丸囲み（①②）や仮名に化けます。
- **項目名と値を「位置」で対応付ける**。並び順で対応付けていたため、
  項目名の直後に紛れ込んだ認識ミスの断片を値として拾い、正しく読めていた
  値を取りこぼしていました。看板は表なので、同じ段で右にあるものが値です。
- **項目名の1文字違いを許す**。「測点」が「剱点」と読まれるだけで
  対応付けに失敗していました。語彙が決まっているので近いものに寄せます。
  この場合は確信度を下げて、レビュー画面で目立たせます。
- **表の罫線を消す**。そのまま読ませると横罫線が「一」「ー」として
  認識され、実際の記入内容を押しのけます。

数字は生成した見本に対するものです。実際の手書き文字はこれより低くなります。
だからこそ、読み取り結果は必ず確認画面を通す設計にしています。

### 運営管理コンソール（`/admin`）

サービス運営側が使う画面です。顧客企業の「管理者」ロールとは別で、
`users.is_platform_admin` が立っているアカウントだけが入れます。

- 全社の契約状況・ユーザー数・現場数・写真数・保存容量の集計
- 会社の一覧と停止／再開（停止するとその会社の全員がログインできなくなります。
  すでにログイン中の人もその場で使えなくなります）
- 全社のユーザー一覧と停止／再開
- **パスワード再設定リンクの発行**（運営が新しいパスワードを決めて伝える形にはしていません。
  他人のパスワードを知っている状態を作らないため、本人が設定する導線を渡します）
- **ログイン履歴**（成功・失敗の両方。「心当たりのない時刻にログインがある」という
  問い合わせに答えるための画面です。存在しないメールアドレスでの試行は、
  会社を特定できないため記録していません）
- お問い合わせの一覧・対応状況の管理・**回答内容の控え**
- **アクセスログ**（別枠・後述）
- **お知らせの配信**（全社宛／会社指定、種別、掲示期間つき。利用者の通知画面と
  ベルに表示され、既読の数も確認できます）

運営管理者の権限は画面からは付与できません（DB で直接立てる運用です）。
顧客の操作で誤って全社閲覧権限が生まれることを防ぐためです。
また、写真そのものは扱いません。公共工事の成果品を運営側が閲覧できる状態は
お客様に説明がつかないため、件数の集計に留めています。

#### アクセスログ（閲覧は1アドレスのみ）

利用者がどの画面を見たかを全社横断で記録し、`/admin/access-logs` で
閲覧数・よく使われる機能・端末・時間帯・利用者ごとの動きを確認できます。

**運営管理者であっても、決められた1アドレス以外は開けません。**
他の運営管理者には存在しない画面（404）として扱われ、メニューにも出ません。
利用者一人ひとりの行動が分かる記録であり、「運営だから見てよい」の範囲を
超えていると考えたためです。権限（is_platform_admin）ではなく
アドレスで固定しているので、データベースを直接書き換えても閲覧者は増えません。

閲覧できるアドレスは環境変数 `ACCESS_LOG_VIEWER_EMAIL` で決まります
（既定: `ten.dev1024@gmail.com`）。このアドレスで新規登録すると、
運営管理者の権限も同時に付きます。

記録は応答を返したあとに書き込むため、画面表示は遅くなりません。

> **実運用の前に、プライバシーポリシーへの記載をご検討ください。**
> 個人の閲覧履歴を残す機能です。

### クラウド共有と権限管理

- 会社 → 現場 → アルバム → ファイルの階層でデータを管理します
- 権限は **38 種類の操作単位** で定義され、ロールに割り当てます
- 既定ロール：オーナー／管理者／現場監督／編集者／撮影者／閲覧者／協力会社
- 「写真は削除できるが台帳は削除できない」といった独自ロールも、コード変更なしで作成できます
- 協力会社など他社のユーザーは、明示的に付与された現場のみアクセスできます（権限の継承はありません）
- 期限付きの外部共有リンク（パスワード・ダウンロード可否・閲覧回数制限つき）を発行できます
- すべての操作は監査ログに追記され、「いつ・誰が・何を」を後から確認できます

### 出力

- **Excel（.xlsx）** — 既定の台帳書式で出力できるほか、発注者指定の `.xlsx` 雛形に
  `{{工事名}}` 形式のプレースホルダを書いておけば、その書式のまま差し込めます。
  発注者ごとに台帳の書式が違うため、書式を固定しない設計にしています
- **PDF** — 提出・印刷用。1 ページあたりの写真枚数を 1 / 3 / 4 / 6 枚から選択できます。
  Chromium の印刷機能で生成するため、日本語の禁則処理・字詰めが崩れません
- **電子納品（CALS/EC）** — `PHOTO/PIC`・`PHOTO/DRA` 構成、`PHOTO.XML`（Shift_JIS）を
  ZIP で出力します。署名が検証できない写真が含まれる場合は出力を停止します
- **Word（.docx）** — 写真の下に管理項目の表と説明文を置いた文書の体裁。
  先方が文章を書き足す前提の報告書に使います

## セットアップ

### 1. 依存パッケージのインストール

```bash
npm install
```

### 2. 環境変数の設定

```bash
cp .env.example .env
```

`.env` を開き、`AUTH_SECRET` を生成した値に置き換えてください。

```bash
openssl rand -base64 32
```

### 3. データベースの起動

```bash
npm run dev:db
```

PGlite（WebAssembly 版の PostgreSQL）を PostgreSQL のワイヤプロトコルで公開します。
アプリからは通常の PostgreSQL と区別がつかないため、`DATABASE_URL` も接続コードも
本番と同じまま使えます。データは `.pgdata/` に入ります。

すでに PostgreSQL を用意している場合は、`DATABASE_URL` をそちらに向けるだけです。
この手順は不要です。

> **同時接続は1本まで**
> `dev:db` は一度に1つの接続しか受け付けません。開発サーバーを起動したまま
> psql などから接続すると切断されます。そのため開発時の接続プールは 1 にしています
> （`DB_POOL_MAX` で変更可）。並行処理が必要なら通常の PostgreSQL を使ってください。
>
> この制限のため、`npm run build` したものを `npm start` で動かす場合は
> `dev:db` を使えません（本番サーバーは複数の接続を張るため `ECONNRESET` で落ちます）。
> 本番ビルドの動作確認には通常の PostgreSQL を用意してください。

### 4. マイグレーションと初期データ

```bash
npm run db:migrate
npm run db:seed
```

シードを流すと、以下のアカウントでログインできます。

| `taro.yamada@example.com` | `password1234` | オーナー |
| `hanako.sato@example.com` | `password1234` | 編集者 |
| `ichiro.suzuki@example.com` | `password1234` | 閲覧者 |

運営管理コンソール（`/admin`）のアカウントは別です。

> **本番では必ずパスワードを変更してください。**
> このアカウントは会社の境界を越えて全社の情報を閲覧できます。

## ファイルの保存先

既定ではローカルディスク（`STORAGE_DIR`、既定 `./.storage`）に保存します。
開発時に追加のサービスを立てずに済ませるためです。

`S3_BUCKET` / `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` をすべて設定すると、
保存先が自動的に S3（および S3 互換ストレージ）に切り替わります。
呼び出し側のコードは変わりません。

| | ローカル | S3 |
| --- | --- | --- |
| 閲覧 URL | `/api/files/...`（都度セッションと所属組織を確認） | 期限付き URL |
| 直接アップロード | 不可（API 経由で受け取る） | 期限付き URL を発行 |
| 複数サーバーでの共有 | 不可 | 可 |

本番では S3 を使ってください。ローカル保存はサーバーを複数台にすると共有できません。

## テスト

```bash
npm test           # ユニットテスト（41 件）
npm run typecheck  # 型チェック
npm run lint       # Lint
npm run smoke      # 画面操作のスモークテスト（要: サーバー起動 + Chrome）
npm run smoke:auth # 認証まわりのスモークテスト（要: db:seed 実行済み）
```

> **スモークはシードのアカウントでログインします。**
> 本番にはデモデータを置かないため、本番に向けて流すとログインで止まります。
> 開発用の環境に対して実行してください。

`npm run smoke` は実際のブラウザで画面を操作し、黒板エディタの編集・写真の選択・
台帳の枚数切替・電子納品の適合チェックなどが動作することを確認します。

`npm run smoke:auth` は新規登録からログアウトまでを通しで確認します。
セッションを偽造せず実際にフォームを送信するため、認証の不具合を取りこぼしません
（新規登録の確認のため、実行のたびにアカウントが1件増えます）。

> **注意**
> 開発サーバーには必ず `http://localhost:3000` でアクセスしてください。
> `127.0.0.1` だと HMR の WebSocket が接続できず、React のハイドレーションが
> 行われないため、画面上のすべての操作が無反応になります。

> **画像を差し替えても表示が変わらないとき**
> `next/image` は最適化結果を **`.next/dev/cache/images`** にキャッシュします
> （`.next/cache` ではありません）。同じファイル名のまま中身だけ差し替えると
> 古い画像が表示され続けるため、次のように消してから再起動してください。
>
> ```bash
> rm -rf .next/dev/cache/images
> ```
>
> キャッシュは幅ごとに保存されます。ブラウザが実際に読むのは srcset 中の
> 1 つ（多くは `w=640`）なので、別の幅だけ確認しても気づけません。

ユニットテストは写真処理と出力処理を対象としています。
特に **EXIF の撮影日時の扱い** は重点的に検証しています。

EXIF の日時にはタイムゾーン情報がありません。
一般的なライブラリはこれを「サーバーのローカルタイムゾーン」として解釈するため、
デプロイ先によって撮影年月日がずれ、深夜に撮影した写真が前日の台帳に入ってしまいます。
本実装では EXIF の文字列を自前で解析し、日本時間として確定させています
（カメラが UTC オフセットを記録している場合はそちらを優先します）。

## 権限モデル

アプリケーション内のどこにも「管理者かどうか」という判定はありません。
すべて「その操作の権限を持っているか」で判定します。

```ts
// 現場に対する権限を解決し、必要な権限がなければ例外を投げる
await requireProjectCapability(userId, projectId, 'photo.delete');
```

自社の現場か、他社（協力会社）の現場かで挙動が異なります。

- **自社の現場** — 現場ごとのロールが優先。なければ会社全体の既定ロールが適用されます
- **他社の現場** — 明示的に付与された権限のみ。継承は一切ありません

この区別により、協力会社のユーザーが権限を付与されていない現場を見ることはできません。

## 電子納品への対応方針

公共工事での利用を前提に、以下を設計に織り込んでいます。

- **小黒板情報電子化（JACIC）** — 黒板情報を JPEG に埋め込み、改ざん検知の署名を保持します
  - 署名の検証状態は写真ごとに `unsigned` / `pending` / `valid` / `invalid` / `error` で記録します
  - 電子納品モードが ON のとき、検証できない写真が含まれていると出力を自動停止します
- **デジタル写真管理情報基準** — `PHOTO/PIC`・`PHOTO/DRA` のフォルダ構成、`PHOTO.XML` の出力
- **有効画素数** — 黒板の文字が判読できることを目安に、100 万画素程度を推奨値としてアップロード時に判定します
- **原本の非改変** — 撮影された元データは再エンコードせず保持します。
  再圧縮は改ざん検知の署名を壊すうえ、写真の編集にあたるためです
